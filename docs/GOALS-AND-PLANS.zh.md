# 目标与计划

本功能纳入 Koder CLI 0.6.1；旧 0.5.21 安装包不包含这些命令。先运行 `koder --version` 核对版本，具体验证范围见发行说明。

Koder 把目标、验收条件、计划、工具回执和费用计数保存在同一个会话中。目标描述要交付什么；计划把它分成可以核对的步骤。计划复用内核 `todo_set`，执行复用原来的 Agent 循环、审批、取消和工具。

## 一句话开始完整任务

普通 `koder` / `koder chat` / `koder run` 任务也可以持续执行，不必先学习目标命令。例如：

```text
把当前项目做成可以交付给新同事使用的版本。先问清缺少的需求，
再完成实现、检查和使用说明，最后给我实际文件与启动方式。
```

Koder 先读取已有材料，理解对象、范围、限制和完成标准。关键条件不明确时，通过原 `ask_user` 询问，每轮聚焦最多三项；已有答案不重复询问。用户回答后，把需求摘要和验收标准存入同一会话的 Todo `brief`，把工作拆成有依赖的步骤，再开始执行。

执行时，完成一部分会继续下一项已获授权的步骤。模型如果过早回复“第二部分要继续吗”，内核会检查本轮仍未完成的计划并继续。只有内容为空的阶段确认会自动交回模型，记录为 `TASK_PHASE_ALREADY_IN_SCOPE`，不会伪造用户选择；改变交付形式、新范围、发信、付费、登录或权限问题仍须实际处理。如果用户明确要求“每一步先问我确认”，保留这种工作方式。

阶段总结不是最终交付。文件、代码和网站仍走原交付检查；文件存在、Todo 打勾或“已完成”文字都不能替代实际核对。最后应说明交付了什么、文件位置或实际预览入口、已运行的验证和仍存在的限制。

在同一项目里可用 `/plan show` 查看保存的需求摘要和步骤；运行中可继续输入补充，沿原 steer / queue 规则处理。`Esc` / `Ctrl+C` 可取消。已完成文件和原回执保留；重启或仅打开会话不会自动启动旧计划。需要恢复时明确提出继续要求，先读回已有结果，再更新本轮计划。需要跨回合累计目标费用和逐条件验收时，使用下面的显式 `/goal` 命令。

这允许复杂任务在同一任务中执行半小时、一小时或更久，**不是故意拖长简单任务，也不是保证所有任务都能在该时间内完成**。默认没有固定工具轮数或任务总时长限制；服务商请求超时、用户设置的费用/步数/时间预算仍有效。连续两次阶段复核没有新的有效工具结果时停止空转，返回 `TASK_PLAN_NO_PROGRESS`。只是反复读取同一内容或修改计划标签，不算实际进展。

无交互的 `run --json` 不等待可选问题。必要输入缺失时输出具体卡点，不能假装已经收到回答；可逆假设必须披露。仅要求计划、只读分析和简单问答不会因为这套策略变成自主执行。

## 显式设置目标与计划

进入项目目录，运行 `koder`，依次输入：

```text
/goal set 整理当前项目的安装说明 --criteria "安装步骤可照做;命令经过实际检查"
/plan create
/plan show
/goal run
```

1. `set` 保存目标，不调用模型，不执行项目操作。省略 `--criteria` 时以目标本身作为验收要求。
2. `plan create` 使用当前模型和只读计划模式，可以阅读资料、询问缺失信息，并通过 `todo_set` 保存步骤。它不会因为生成计划就开始改文件。
3. `plan show` 查看完整步骤、状态与依赖。可继续要求模型调整计划，或导入自己编写的计划文件。
4. `goal run` 明确启动或继续这个目标，仍按当前审批设置执行。只读发现、已经批准的实际操作和验收结果都进入原会话记录。

运行时输入框保持可用，原来的引导和 FIFO 排队方式不变。`Esc`、`Ctrl+C`、`/goal pause` 停止当前执行；`/goal cancel` 取消目标。暂停后用 `/goal run` 或 `/goal resume` 继续，已完成结果保留。`/goal show` 查看目标、原因码和条件是否有验收回执。

底部仍使用原 Todo 行，紧凑显示目标状态和步骤进度；不会新增整页任务界面。`Ctrl+T` 继续展开或收起计划。

## 终端命令与脚本

在同一项目目录使用同一个 `--session`，才能继续同一份目标：

```bash
koder goal set "整理安装说明" --criteria "保存说明文件;核对其中的命令" --session docs
koder plan create --session docs
koder plan show --session docs
koder goal run --session docs
koder goal show --session docs --json
koder goal pause --session docs
```

`goal run --json` 输出原 JSON 事件流，最终 `result` 包含 `goal`、`plan`、退出码、完成状态和费用记录。未满足验收条件时不能返回已完成。`goal show --json` 则只输出当前记录，不重新调用模型。`--approval deny` 仍禁止写入；`--yes` 仍不授予电脑权限、不代替登录或高风险操作的专门确认。

没有独立目标也可以使用 `koder plan create "任务要求"`、`koder plan show`、`koder plan run`。其中 `plan run` 使用原执行循环；希望逐条件验收时先设置目标。

`goal revise "调整后的目标" --criteria "新条件一;新条件二"` 保留目标 ID、已完成回执和费用历史，清除旧条件的验收标记，要求重新核对。目标取消或完成后，再 `goal set` 会归档前一个目标及计划。不同项目、账号和命名会话相互隔离；一个会话同时只推进一个目标。显式目标执行遇到被其他窗口占用的会话会报 `MEMORY_BUSY`，不会悄悄换成空会话。

## 导入自己写的计划

在项目内保存 `plan.json`：

```json
{
  "items": [
    {"id":"inspect","title":"核对当前安装过程","status":"pending"},
    {"id":"write","title":"修改安装说明","status":"pending","dependsOn":["inspect"]},
    {"id":"verify","title":"核对文件和命令","status":"pending","dependsOn":["write"]}
  ]
}
```

然后运行 `koder plan set plan.json --session docs`，或者在对话中输入 `/plan set plan.json`。只读取项目内的文件，文件上限 256 KiB。需要追加一项时使用 `/plan add 核对 Linux 安装步骤`。

计划沿用稳定 ID、依赖、优先级、排序、负责人和 revision。循环依赖、缺失依赖或修订冲突会拒绝整次修改，保留旧计划。模型用 `todo_set op=read` 读取当前 revision 后再合并修改，不应反复覆盖已完成的项目。

## 完成判定和恢复

目标只有同时满足以下条件才标记 `completed`：

- 原执行回合及文件、网站等已有交付检查成功。
- 计划非空，全部步骤完成。
- 每个验收条件都通过 `goal_report verify` 引用本目标执行中的实际工具回执，并说明它如何满足要求。
- 没有尚未核实的副作用。

`goal_report` 只能读取目标、提交验收说明或报告卡点，不能创建目标、启动执行、授予权限或自行把目标标为完成。计划打勾、无关任务的回执、失败或未知的结果均不能作为验收证据。调整目标后必须重新验收；计划的步骤或依赖改变后也需要重新核对。验收说明由模型结合真实回执给出，不能替代人工对复杂结论、法律意见或主观设计质量的判断。

模型先调用 `goal_report read` 获取当前 revision 和有效回执编号，再提交验收。回执每页最多 20 条，可以继续读取；无需搜索本机日志。每次验收返回新 revision，后续验收使用这个值。计划生成回合如果没有保存任何步骤，会返回 `GOAL_PLAN_MISSING`，不会把一段对话说明当成已保存计划。

| 原因码 | 含义与处理 |
| --- | --- |
| `GOAL_PLAN_MISSING` | 尚未保存计划，先制定具体步骤。 |
| `GOAL_PLAN_INCOMPLETE` | 还有未完成、受阻或失败的步骤，检查已有结果后继续。 |
| `GOAL_CRITERIA_UNVERIFIED` | 缺少条件验收回执，继续实际核对。 |
| `GOAL_PLAN_CHANGED_REVERIFY` | 计划内容发生变化，重新核对条件。 |
| `GOAL_EVIDENCE_INVALID` | 所引用的结果不属于本目标、失败或未核实，读取正确结果后再提交。 |
| `GOAL_NEEDS_INPUT` | 缺信息、绑定、授权或外部条件，原因保存在目标 note。 |
| `GOAL_INTERRUPTED` | 用户取消或进程中断，暂停并保留回执。 |
| `TASK_COST_BUDGET_EXHAUSTED` / `TASK_COST_UNCONFIRMED` | 沿用费用预算或未确认费用保护，不能靠继续目标重置。 |
| `SHELL_RECONCILIATION_REQUIRED` | 旧操作结果未知，先按原核对流程处理；目标命令不能解除它。 |
| `TASK_PLAN_CONTINUE` | 阶段汇报之后还有就绪步骤，正在同一任务内继续；不是错误。 |
| `TASK_PLAN_NO_PROGRESS` | 连续阶段复核没有新的有效工具结果，停止空转并保留已有产物。 |
| `TASK_PLAN_NEEDS_INPUT` | 真实拒绝、缺失条件或依赖阻塞；查看 Todo notes 和已有回执。 |
| `TASK_PLAN_INCOMPLETE` | 执行中的计划被清空，不能以空清单宣称完成。 |

按计划持续执行与失败后的补交付不同：有实际进展的多阶段工作不会被“两次补交付”额度截断。清单完成后，明显缺少交付的正常本地回合仍走既有的最多两次补交付检查；取消、拒绝授权、未知副作用、费用限制仍优先。无法完成时保存 `blocked` 和原因，不能用空泛回复假装成功，也不自动重放外部提交。

## 保存、费用与常驻进程

目标和计划进入原会话检查点，没有第二套数据库、额外 Skill 包或新的执行器。重启后读取记录不会自动跑任务；确认继续时再输入 `/goal run`。工具次数仍按现有设置默认不设固定上限；用户明确设置的步数上限仍有效。规划和多次继续的费用计数累计到同一目标，保留原价格配置、调用预留和未知费用检查。创建新目标才开始新的目标账目。

启用 agentd 时，前台通过现有认证 IPC 操作同一内核会话；没有启用时可直接在前台使用，不要求安装系统服务。该功能不会因设定目标就另建定时任务，也不承诺关闭前台后自动继续执行。断开客户端仍遵守现有取消规则。

持久命令需要会话记忆，不与 `--no-memory` 或 `--new` 混用。交互聊天明确选择 `--no-memory` 时，目标只保留在该聊天进程内。当前实现使用 Koder 内核；切到外部执行引擎时会给出 `GOAL_ENGINE_UNSUPPORTED`，不会声称另一引擎已具备这些行为。

## 实现依据

参考了 [Codex 的公开计划工具实现](https://github.com/openai/codex/blob/e9854c0aa52d494fa4f4c3683741461e2640011b/codex-rs/core/src/tools/handlers/plan.rs) 对计划更新和事件输出的处理方式。Koder 的实现使用自己的会话目标协议、现有 Todo、工具回执与执行循环，没有复制上游执行器，也没有新增外部依赖。

持续执行补充参考了 [LangGraph 的执行循环与检查点处理](https://github.com/langchain-ai/langgraph/blob/main/libs/langgraph/langgraph/pregel/_loop.py) 和 [Anthropic 的长任务工程说明](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents)。这里借鉴的是保存进度、增量完成和明确完成条件的设计；执行仍在 Koder 原内核内，没有引入这些项目的运行包或复制代码。

## 本地复验

1. 在独立项目中提交含两部分的任务，回答前置问题；确认 `brief` 保存了实际需求，只有一条根请求。
2. 第一部分写完后，若模型仅询问下一阶段是否继续，确认内核继续，第二部分真正落盘并读回。
3. 用六个阶段重复验证，确认不会在第二次阶段汇报后停下，费用与工具计数不重置。
4. 取消、拒绝写入、设定费用或步数上限，确认都能停止；打开旧会话不自动执行剩余步骤。
5. 连续空谈或重复相同读取时确认返回原因码；前置必要信息仍缺失时不能假称交付。

自动化验证包含真实本地文件工具和脚本模型的故障注入。真实模型记录、实际持续时长、Windows/Ubuntu 实机及图形验收须分别记录，不能以脚本测试代替。
