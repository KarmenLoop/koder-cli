# 009 · 代码审查：带着上下文挑毛病

单元 1 · 建议 35 分钟（含自行练习） · 0.4.16 配套教材

[课堂](../index.zh.html#lesson-9) · [总纲](../README.zh.md)

## 学习目标

得到带位置、影响和复现方式的审查结果，并防止JSON解析失败假通过。

## 原理讲解

review 不只盯着改动本身。它会读仓库里的规则文件（比如 AGENTS.md）、最近的提交，还会去找被改函数在别处的调用，再让模型带着只读工具核实。
每条问题都有级别（高、中、低）、文件、行号和修改建议。常用写法：

专题补充
审查意见应连接代码位置、触发输入、实际影响与可行修复。它不是批量挑文风，也不由意见数量衡量质量。审查者需要知道变更前行为和项目约束；机器可读审查还要验证输出解析成功，空列表只有在有效结构中才有意义。

先读需求与最小相关代码，再手算一个正常例和一个失败例。写意见时只保留能够说明用户影响的发现，附路径和紧凑行号。对每条建议想一个可能推翻它的反例，分清必修错误与可选风格。

## 准备

在自己的测试仓库准备一处可解释的变更；没有Git仓库或没有变更时先明确审查范围。

### 跟做 1：定位操作入口

先分清屏幕上的系统终端和 Koder 提示符。系统命令在终端运行；以 / 开头的会话命令放在 Koder 对话中。把本课出现的目录逐个写入 environment.md，并标注“当前目录”“临时练习”“正式作品”。

检查点：能指着一条命令说明由谁解释、在哪个目录发生；不同目录不被画成同一个对象。

### 跟做 2：先预测再操作

将本课输入逐项编号。执行前先写一句预期，再按本课任务操作一次。需要点击或审批时，记录选项名称与选择理由；无操作环境则只完成推演栏。

检查点：实际输出与事前预期分开，拒绝或取消也有明确结果。

### 跟做 3：读回产物

不要只看最后一句回复。打开实际文件，或重新读取目标状态，记录与要求对应的行、字段或画面。临时目录退出后可能被清理，需要留存时按教练提示保留。

检查点：作品路径可找到；模型陈述与文件内容能相互核对。

### 跟做 4：独立再做一遍

只替换题目指定条件，保留原结果。用自己的话解释哪些步骤保持、哪些步骤改变。请同学从记录中复做，不替对方补隐含步骤。

检查点：变式有独立结果；接手者不用猜目录或输入。

### 本课交件自评

每项 0–2 分：缺失或错误 / 有结果但缺依据 / 结果与依据齐全。

- 能区分终端、Shell、CLI 与文件对象
- 操作前有明确预期，操作后有实际读回
- 取消、拒绝或临时目录清理的后果解释正确
- 变式保留原条件并指出变化
- 小作品可打开，记录足以供另一人复做

### 开发者复盘

把入口、工作目录和产物路径显式传入测试。练习取消发生在修改前与修改后两种情况；断言未批准变更未落盘、已完成产物可读回。不要用“收到成功字符串”代替文件断言。

工作簿结构检查只能提示哪些栏目未填；正确性仍须核对本课输入、结果、变式和参考答案。

## 手把手操作

1. 先用 git diff 查看本次变更，再运行 koder review。

   应看到：审查对应真实差异；每个问题应包含位置、触发条件、影响和建议。

2. 挑一项自己复现，确认能触发，再要求最小修复。

   应看到：不因模型提出问题就全盘改动；无法复现的标为待核对。

3. 需要机器处理时运行 koder review --format json，保存stdout、stderr和退出码。

   应看到：可解析、parsed状态与退出码均符合本版契约；空仓错误不能按0通过。

4. 修复后复跑原测试并再次审查相关差异。

   应看到：原问题关闭有证据，未修项列出原因；审查不等于自动部署。

5. 按位置、触发、影响、建议四句写发现

   应看到：说明返回12而应36，建议乘qty并加数量大于1用例

   为什么：具体例子比“逻辑可能有问题”可操作

6. 改变条件：qty固定为1的业务

   应看到：先核业务约束，此输入不能证明缺陷影响

   为什么：验收检查发现是否可复现、是否属于本次改动、是否具有准确位置。JSON失败必须保留为失败；没有发现不能自动推出项目无缺陷。修复后重新验证触发例而非只关闭评论。

## 故障恢复

- **REVIEW_UNPARSED**：保留原输出，按失败处理；不要手填parsed=true。

- **建议与当前文件不符**：核对分支、工作区和未提交变更；重新限定范围。

## 作业

给购物车修复做一次审查：至少一条真实问题或明确无可证问题的结论，附测试依据。

## 自查与参考答案

## 开发者教学

把review作为数据接口：校验JSON结构、退出码与parsed，不只搜索“通过”。
负例覆盖解释性散文、空结果、部分JSON与服务错误；保持REVIEW_UNPARSED非零。
CI在只读令牌和受限工作区里运行；评论或推送是独立授权动作。

开发者加餐
结构化审查状态与发现数组应分开建模。解析失败可有诊断和非零退出，不能回退成空数组。上下文裁剪应保留关键调用者与数据约束，否则局部正确意见可能全局错误。
