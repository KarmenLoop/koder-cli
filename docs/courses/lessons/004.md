# 004 · 第一个任务：看懂差异，决定写不写

单元 1 · 建议 30 分钟（含自行练习） · 0.4.15 配套教材

[课堂](../index.zh.html#lesson-4) · [总纲](../README.zh.md)

## 学习目标

把一句模糊要求改成可验证交付；看清每一处差异，拒绝或批准后核实磁盘。

## 原理讲解

练习场里的 cart.mjs 算总价时忘了乘数量，测试一直挂着。我们让 Koder 来修。
默认交互模式下，Koder 改文件之前先给你看差异：以 - 开头的红色行会被删掉，以 + 开头的绿色行会加进来。本课需要输入 y 才写入，输入别的就作罢；开启 --yes 会自动批准普通修改。
练习场采用逐项确认，让你看清每一步。实际使用默认智能判断：低风险命令与普通项目修改自动运行；敏感操作可选择始终允许。/permissions execution status 查看，ask 切回逐项确认，reset 撤销全部设置。

专题补充
差异是从旧内容到新内容的变换说明。新增和删除行能够展示实现，却不能自动解释业务是否正确。审阅小修改时先固定输入输出，再读每个 hunk 的上下文，最后检查批准或拒绝后的实际文件。任务越模糊，越容易把界面上的合理文案误认为已经完成的作品。

先用一个三行需求说明对象、变化和验收，再把差异逐行翻译为行为。计算至少一个会改变结果的例子，并保留一个不该改变的例子。审批针对具体差异；完成后从磁盘重读相关片段，对照测试与原要求，保持需求、代码和结果一致。

## 准备

用教程购物车或附带cart-lab，不直接拿重要工程练手。自建项目先记录未提交改动，别覆盖原有工作。

## 手把手操作

1. 输入任务：“修复购物车总价，数量必须参与计算；保留其他功能，补空购物车测试，运行 node --test。”

   应看到：目标包含范围、约束和验收命令；任务不能只有“优化一下”。

2. 查看拟修改文件与差异，第一次选择拒绝。

   应看到：拒绝后原文件仍相同；不能只看聊天里一行“没改”。

3. 再次执行，确认只改目标函数和相关测试后批准。

   应看到：写入发生在指定项目；不顺手全仓格式化，不添加无关依赖。

4. 自己打开文件，运行检查，并让 Koder 列出修改、验证结果和未完成项。

   应看到：文件内容、测试输出、最终汇报三者一致；失败时保留原始输出。

5. 写一条只修改数量计算的任务卡，列出输入和断言

   应看到：任务卡要求12×3=36，保留显示格式与其他功能

   为什么：可计算目标让修改范围明确，也让测试有独立答案

6. 改变条件：输入变为两行12×3与5×2

   应看到：预期总额46，验证遍历与乘法都生效

   为什么：检查范围包括目标文件、非目标文件以及用户已有修改。逐行解释比只看增删统计更有价值；测试应能区分改前和改后。输出契约写清哪些值保持、哪些值变化，以及拒绝后应保持什么内容。

## 故障恢复

- **只回答了思路，没有落盘**：改用执行任务并指定文件与验证命令；先确认当前不是只读ask或计划模式。

- **出现未知执行结果**：先检查文件和回执，不要求把已完成操作全部再做一次。

## 开发者教学

把用户需求拆成输入、输出、边界值与不变量。优先写能抓住真实bug的测试，而不是复制实现。
用git diff --check检查空白问题、git diff核范围；测试成功也要检查有没有偷偷删除断言。
交付记录包含工作区、文件、测试命令和退出码；模型最终文字不能代替文件。

开发者加餐
写入最好基于实际读过的版本，发现用户并发改动时重新比较。diff 展示必须保留上下文和路径，不能只渲染模型口述。验证程序要独立于实现计算预期，避免把错误函数的结果当正确答案。
