# 109 · 红绿回归：保留失败证据

## 学习目标

完成「红绿回归：保留失败证据」的操作练习，能够解释结果、诊断常见问题并提交可核对的作业。

## 原理讲解

回归测试需要证明旧版本确实出错、修复版本确实通过。先写或运行失败用例，再修改实现，保留两次输出和源码标识。一次命令出错可能来自环境而非目标bug，因此要确认失败位置。红绿不是把测试脚本改两次制造表面变化。

专题补充
红绿回归说明同一规则在旧实现失败、修复实现通过。失败必须来自目标行为，环境错误与测试发现失败要分开。保留原输出和版本，才能让审查者知道检查的到底是哪份代码。

先固定输入、预期与断言，再运行旧版保存红灯；修改实现后运行同一断言并保存绿灯。新增边界可以追加，不能用修改答案取代修复。

## 准备

先完成第108课。使用自有Koder Projects练习目录和合成数据；阅读示例不会执行命令。需要运行脚本时先核对本机运行时；不为阅读课程自动安装任何软件。


两次使用相同输入与预期，仅实现按修复变化。

### 跟做 1：从风险写预期

先列本课要防止的错误，再写应通过和应失败各一个输入。预期由业务规则推导，不能复制待测函数输出当答案。

检查点：每条检查都有失败含义，空结果不会自动算通过。

### 跟做 2：证明检查能失败

在自有副本中故意破坏一处相关输入或实现，运行同一检查，保存失败输出后恢复。不要删断言来让基线变绿。

检查点：能看到对应断言失败或非零退出，证明入口确实被调用。

### 跟做 3：固定条件再复测

保留版本、命令、cwd、数据和退出码。不同平台或账号层独立记录；复测仍使用原断言与合理时限。

检查点：通过结果对应当前文件；历史失败也保留。

### 跟做 4：做接手者复现

复制验收包到新目录，只按 README 操作，补全隐含前提。变式后说明哪些检查失效、哪些需要新增。

检查点：另一人能从说明找到输入、命令、预期和实际结果。

### 本课交件自评

每项 0–2 分：缺失或错误 / 有结果但缺依据 / 结果与依据齐全。

- 检查与实际风险对应
- 有可观察的失败基线
- 断言独立且退出码正确
- 平台、账号和模拟层分清
- 换目录可复做并保留原失败

### 开发者复盘

测试桩只替换外部边界，核心行为必须真的调用。增加坏参数、取消、UNKNOWN 和路径漂移用例。不要把模拟 Windows 平台值当成 PowerShell 或 GUI 真机结果。

工作簿结构检查只能提示哪些栏目未填；正确性仍须核对本课输入、结果、变式和参考答案。

2. 冻结输入与断言

   应看到：保存测试文件。

3. 运行旧实现

   应看到：确认目标断言失败。

4. 修改实现

   应看到：不改正确答案。

5. 运行并保存绿灯

   应看到：同时检查其他回归。

6. 整理本次实际结果与仍未确认的内容，把证据链接到作业。

   应看到：记录与「两次使用相同输入与预期，仅实现按修复变化。」逐项对照，不把未执行项填成通过。

7. 保存失败断言与调用输入 将上述完整程序保存为自有目录的 case.mjs，运行 node case.mjs；先独立预测输出，再与固定输出对照。

   应看到：明确200≠600的业务红灯
   Node 固定输出：{"old":200,"fixed":600,"expected":600,"oldPass":false,"fixedPass":true}

   为什么：不是所有非零退出都能证明此缺陷

8. 改变条件：输出为SyntaxError

   应看到：分类语法失败，数量规则尚未运行

   为什么：核对命令、工作目录、退出码、失败位置与源码身份。只截最后一行会漏掉实际测试数量；绿色输出也可能来自旧进程或另一份文件。

## 故障恢复

- **结果与示例不一致**：初始化失败不能冒充业务红灯；要说明是否真正进入目标路径。 先保存原始错误，再从第一次偏离预期的步骤定位。

- **当前环境不能完成真实操作**：完成资料阅读、合成演练和验收计划，标明缺少的账号、运行时或设备。不要伪造回执，也不要为了过课扩大授权。

## 开发者教学

原失败不可覆盖；证据记录包括命令、环境、版本和退出码。
实现前固定输入、输出、错误与权限契约。为本课关键边界设计一个应通过与一个应拒绝的用例。
交付时记录源码/配置版本、实际命令、退出码、产物及回退方式；静态检查不替代真实账号或设备验收。

开发者加餐
证据应在结果判定前可靠保存，哈希标识内容而非证明行为。测试工具错误需要单独修复与重跑授权，不将一次环境失败包装成业务基线。
