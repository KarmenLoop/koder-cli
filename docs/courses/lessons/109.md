# 109 · 红绿回归：保留失败证据

单元 8 · 建议 30 分钟（含自行练习） · 0.4.15 配套教材

[课堂](../index.zh.html#lesson-109) · [总纲](../README.zh.md)

## 学习目标

完成「红绿回归：保留失败证据」的操作练习，能够解释结果、诊断常见问题并提交可核对的作业。

## 原理讲解

回归测试需要证明旧版本确实出错、修复版本确实通过。先写或运行失败用例，再修改实现，保留两次输出和源码标识。一次命令出错可能来自环境而非目标bug，因此要确认失败位置。红绿不是把测试脚本改两次制造表面变化。

专题补充
红绿回归说明同一规则在旧实现失败、修复实现通过。失败必须来自目标行为，环境错误与测试发现失败要分开。保留原输出和版本，才能让审查者知道检查的到底是哪份代码。

先固定输入、预期与断言，再运行旧版保存红灯；修改实现后运行同一断言并保存绿灯。新增边界可以追加，不能用修改答案取代修复。

## 准备

先完成第108课。使用自有Koder Projects练习目录和合成数据；阅读示例不会执行命令。需要运行脚本时先核对本机运行时；不为阅读课程自动安装任何软件。

## 示例与解读

```text
RED：旧实现，数量用例失败，exit1
GREEN：新实现，同一断言通过，exit0

补充案例：确认红灯来自数量缺陷
旧total返回200，断言期望600

可复制的离线 Node 样例（仅计算合成数据或内存时序）：
(async()=>{const old=x=>x.p;const fixed=x=>x.p*x.q;const input={p:200,q:3};return {old:old(input),fixed:fixed(input),expected:600,oldPass:old(input)===600,fixedPass:fixed(input)===600};})().then(value=>console.log(JSON.stringify(value)));
```

两次使用相同输入与预期，仅实现按修复变化。

## 手把手操作

1. 写下本课目标、当前工作区和预期产物。保留练习原件，在副本操作。

   应看到：目标聚焦「红绿回归：保留失败证据」，可与本课示例对照；无无关真实资料。

2. 冻结输入与断言

   应看到：保存测试文件。

3. 运行旧实现

   应看到：确认目标断言失败。

4. 修改实现

   应看到：不改正确答案。

5. 运行并保存绿灯

   应看到：同时检查其他回归。

6. 整理本次实际结果与仍未确认的内容，把证据链接到作业。

   应看到：记录与「两次使用相同输入与预期，仅实现按修复变化。」逐项对照，不把未执行项填成通过。

7. 保存失败断言与调用输入 将上述完整程序保存为自有目录的 case.mjs，运行 node case.mjs；先独立预测输出，再与固定输出对照。

   应看到：明确200≠600的业务红灯
   Node 固定输出：{"old":200,"fixed":600,"expected":600,"oldPass":false,"fixedPass":true}

   为什么：不是所有非零退出都能证明此缺陷

8. 改变条件：输出为SyntaxError

   应看到：分类语法失败，数量规则尚未运行

   为什么：核对命令、工作目录、退出码、失败位置与源码身份。只截最后一行会漏掉实际测试数量；绿色输出也可能来自旧进程或另一份文件。

## 故障恢复

- **结果与示例不一致**：初始化失败不能冒充业务红灯；要说明是否真正进入目标路径。 先保存原始错误，再从第一次偏离预期的步骤定位。

- **当前环境不能完成真实操作**：完成资料阅读、合成演练和验收计划，标明缺少的账号、运行时或设备。不要伪造回执，也不要为了过课扩大授权。

## 作业

交红绿日志、文件哈希和最小差异。

## 自查与参考答案

至少提交明确产物、关键步骤记录和一项失败或边界检查。结合本课判断题核对：不能，它只是前置环境失败。 对真实设备或外部服务没有执行的部分写NOT_RUN。

## 开发者教学

原失败不可覆盖；证据记录包括命令、环境、版本和退出码。
实现前固定输入、输出、错误与权限契约。为本课关键边界设计一个应通过与一个应拒绝的用例。
交付时记录源码/配置版本、实际命令、退出码、产物及回退方式；静态检查不替代真实账号或设备验收。

开发者加餐
证据应在结果判定前可靠保存，哈希标识内容而非证明行为。测试工具错误需要单独修复与重跑授权，不将一次环境失败包装成业务基线。
