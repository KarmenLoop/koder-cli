# 073 · 调试日志：记录状态而不是倾倒数据

## 学习目标

完成「调试日志：记录状态而不是倾倒数据」的操作练习，能够解释结果、诊断常见问题并提交可核对的作业。

## 原理讲解

有用日志说明发生了什么、属于哪个任务、处于哪个阶段。大量原始对象可能泄漏秘密，也让关键错误淹没。给每次操作一个稳定ID，记录开始、完成或未知，并保留可读取的原始证据路径。日志既服务用户，也服务之后的故障重建。

专题补充
日志应回答哪个操作在哪个阶段发生了什么。倾倒完整对象既可能泄密，也容易淹没第一原因。书店结算用operationId关联验证、保存和显示事件，状态与错误码保持结构化，正文只给必要解释。

先列排障问题，再决定字段。在关键边界记录事件，保留发生顺序与原始错误类别；用合成事件重建一次操作，不依赖人工记忆。

### 跟做 2：定位最小改动

### 跟做 4：解释代价和边界

检查点：解释具体到数据、操作或状态，不能只有“更高效”。

2. 确定需要回答的排障问题

3. 在关键边界记录事件

   应看到：不是每行都打印。

4. 模拟一次失败

   应看到：能找到第一原因。

5. 检查脱敏和关联

   应看到：同一操作的记录能串起来。

6. 整理本次实际结果与仍未确认的内容，把证据链接到作业。

   应看到：记录与「结构化字段可过滤；没有凭据和完整私人内容。」逐项对照，不把未执行项填成通过。

7. 写{operationId,stage,state,code}事件

   应看到：四字段可定位操作与失败类别

   为什么：消息“出错了”缺乏可筛选语义

8. 改变条件：再加requestId=r1

   应看到：保留两种关联关系，不把请求重试当新业务操作

   为什么：检查同操作关联、第一失败、终态与脱敏。若有开始无结束，先确定是否仍在运行或记录丢失，不补写成功。排序时不要把不同进程墙钟当绝对全序。

## 故障恢复

- **结果与示例不一致**：后续清理错误不能覆盖最初失败；完整堆栈也不应直接展示在用户聊天中。 先保存原始错误，再从第一次偏离预期的步骤定位。

- **当前环境不能完成真实操作**：完成资料阅读、合成演练和验收计划，标明缺少的账号、运行时或设备。不要伪造回执，也不要为了过课扩大授权。

## 开发者教学

事件先持久化再更新状态；未知不等于零成本或没有副作用。
实现前固定输入、输出、错误与权限契约。为本课关键边界设计一个应通过与一个应拒绝的用例。
交付时记录源码/配置版本、实际命令、退出码、产物及回退方式；静态检查不替代真实账号或设备验收。

开发者加餐
事件与状态投影分离，持久化失败必须明确。高基数字段适合日志但不一定适合指标标签；秘密字段采用允许列表比打印后遮盖更稳妥。
