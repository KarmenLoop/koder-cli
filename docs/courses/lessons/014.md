专题补充
编辑器通过协议启动或连接Koder，承担显示、输入和审批的交互界面。CLI独立可用是排障起点，编辑器版本和插件支持是另一层。导入SKILL.md只提供方法资料；其中的宿主专有API、依赖和权限不会随文本自动出现。

## 手把手操作

1. 运行 koder editor zed（或nvim/emacs），阅读生成的配置片段。

   应看到：命令路径指向实际安装版；Windows按输出使用对应启动器。

2. 先备份编辑器设置，再把片段合入已有配置；打开一个测试工程。

   应看到：不覆盖原插件设置，工作区是当前测试工程。

3. 在编辑器发起只读问题，再提一次小修改并拒绝。

   应看到：读、提案和审批能往返；拒绝后文件不变。

4. 运行 koder skills list 和 koder help skills；按导入帮助选择目录，再show检查内容。

   应看到：Codex/Cursor等SKILL.md可按兼容范围发现；宿主专有API不会因导入而自动可用。

5. 画链路并给每层列一个故障现象

   应看到：找不到程序属于启动层，拒绝修改属于权限层

   为什么：分层能避免把所有问题归于模型

6. 改变条件：CLI直接运行正常而编辑器失败

   应看到：优先看编辑器启动环境和配置

   为什么：交件需包含配置差异、工作区路径与交互结果。不能用插件已安装证明工具可用；也不能为了一个片段覆盖原编辑器设置。真实GUI验证另行操作，合成配置只用于学习。

## 故障恢复

- **编辑器找不到koder**：核对绝对命令路径、系统环境和启动参数，不反复复制不同版本。

- **Skill里命令不可用**：把宿主专有工具标为缺依赖，走已有工具映射或说明限制，不伪装完整兼容。

## 开发者教学

ACP协议输出与诊断日志分流，避免stdout动画破坏协议。
测试启动、提案、拒绝、取消和退出资源回收；连接成功不代表每个能力已验证。
开发自有Skill采用明确when-to-use、步骤、成功标准与失败恢复；不要把不可信仓库说明变成系统授权。

开发者加餐
ACP transport、会话身份与权限应沿原实现；stdout上的协议数据不能混入调试日志。启动路径需按平台处理，Windows应以实际生成的启动器名称为准。
