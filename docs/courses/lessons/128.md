# 128 · 更新邮件：没有变更清单时怎么写

[课堂](../index.zh.html#lesson-128) · [总纲](../README.zh.md)

## 学习目标

完成「更新邮件：没有变更清单时怎么写」的操作练习，能够解释结果、诊断常见问题并提交可核对的作业。

## 原理讲解

发版邮件最容易把旧能力误写成本版新增。先找对应版本的发布记录、CHANGELOG、验收材料或标签差异；没有材料时应明确说明不能确认增量，改写为现有能力使用说明。披露不能成为继续编造新增功能的挡箭牌。

专题补充
增量由前后版本差异确定，而不是由当前功能存在确定。邮件中最有价值的信息通常是用户受什么影响、需不需要升级和升级前要检查什么。已有功能可以提供背景，但要避免“本版新增”归因。缺少完整发布材料时，诚实写已确认项和未确认项比填满卖点更有用。

锁定前后版本，把已有功能、已发布增量、候选与计划分列。按用户影响选择邮件前两条信息，写需要采取的动作和迁移检查；逐条核对新增、修复、支持等归因词。

## 示例与解读

```text
无来源写法：目前没有可核对的本版变更清单，以下说明现有能力及使用方法，不代表本版新增。

补充案例：版本归因：区分新旧与计划
合成发布材料：1.3已支持Markdown标题索引；1.4变更A修复空标题导致任务中断，测试含空文件与无标题文件；变更B输出新增sourcePath字段；已知限制为扫描PDF未支持。讨论帖提到“计划增加云同步”，未见发布条目。旧脚本按固定列号读取CSV，是否受影响需核对实际输出契约。
本课条件：四条材料混在一个功能列表
```

正文不能同时又声称“本版新增X”却无证据。

### 跟做 1：先建事实表

逐条读取本课材料，建立“编号、原文或数据、出处、可支持的结论、不能推出什么”五列。区分历史功能、版本增量、判断和待核实信息。

检查点：每项重要陈述都有依据，缺材料不会被写成新增功能。

### 跟做 2：围绕读者排结构

用一句话写读者读完后应做什么，再安排论点、证据、限制和行动。介绍、更新邮件、对比与压缩稿使用不同结构。

检查点：段落承担不同功能，不靠同义反复凑字数。

### 跟做 3：成稿后反向核对

将正文的数字、产品名、定价、版本和比较结论逐一连回事实表。按本课要求计算正文长度，文件正文与聊天收尾分开。

检查点：删掉无据归因；保留不确定性，但仍交出读者能用的稿件。

### 跟做 4：做受控改稿

只引入给定变式，检查受影响句子和来源。压缩时先删重复，再缩例子，不能新增前稿没有的事实来补流畅度。

检查点：改稿前后事实集合可对照，解释内容取舍而不只说“润色”。

7. 把每条映射到1.3已有、1.4变化或计划

   应看到：交增量表，标题索引归旧能力

   为什么：当前有此功能就写本版新增→核对基线版本

8. 改变条件：若找不到1.3材料怎么办

   应看到：只写1.4材料明确声明的变化，其余不作首次加入时间归因

   为什么：将讨论帖计划写进“新增云同步”→从增量区移除，若必须说明则明确计划未确认发布。

## 故障恢复

- **结果与示例不一致**：不要根据当前功能列表反推某个版本什么时候加入。 先保存原始错误，再从第一次偏离预期的步骤定位。

- **当前环境不能完成真实操作**：完成资料阅读、合成演练和验收计划，标明缺少的账号、运行时或设备。不要伪造回执，也不要为了过课扩大授权。
