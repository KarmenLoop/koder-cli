# 011 · 流程编排与 CI：让智能体排好队

单元 1 · 建议 45 分钟（含自行练习） · 0.4.15 配套教材

[课堂](../index.zh.html#lesson-11) · [总纲](../README.zh.md)

## 学习目标

把重复工作拆成可检查步骤，前一步失败时不让发布步骤继续。

## 原理讲解

把审查、测试、修复写进一份流程文件，本地和 CI 跑同一份。下面是一份小流程，我们直接跑：
koder ci init 会生成 GitHub Actions 工作流：PR 一开就自动审查并评论；在 PR 里评论 /koder fix，它会修好并推回分支。只有仓库成员的评论才算数，路人甲喊破喉咙也没用。

专题补充
流程把输入、步骤和产物连接成有向依赖图。顺序、条件与并行是不同关系：检查失败后可执行诊断，但不应进入依赖成功的步骤。shell步骤也可能写文件，不能因为名称普通就与其他写入并行。课堂先模拟状态，再阅读现有flow-lab，不生成或触发远端CI。

把每一步写成输入→命令→输出，再画依赖箭头。对成功、失败、跳过分别计数，沿条件表达式逐步推演。用给定文件路径检查生产者和消费者是否一致；实际本地练习沿用课程附带flow命令与现有检查。

## 准备

先通过第8–10课。使用附带flow-lab.json和cart-lab；先读文件，再运行。示例只执行本地检查，不发布、不调用模型。

## 手把手操作

1. 打开flow-lab.json，找出每步id、type、run和依赖。

   应看到：每步只有一个可描述的职责；检查命令来自当前项目。

2. 在示例目录运行 koder flow run flow-lab.json。

   应看到：故意有bug的购物车检查失败；保存每步状态，不把后续跳过当成功。

3. 按第10课修复，再运行相同流程。

   应看到：相同输入与流程下检查通过，差异可解释。

4. 需要CI时先运行 koder help ci，再在自己的测试仓库生成并审阅配置。

   应看到：检查权限、分支和Secrets引用；生成文件不等于线上工作流运行过。

5. 画依赖图并标成功与失败条件

   应看到：C依赖B成功，D依赖B失败

   为什么：终止和失败处理可以同时发生

6. 改变条件：要求D无论结果都执行

   应看到：把D改为always语义，仍不让C消费失败结果

   为什么：验收需要每步状态、最终退出和产物对应。确认失败分支能解释原因，成功分支只消费成功产物；并行收益应由耗时计算和无冲突证明支持。

## 故障恢复

- **并行步骤互相覆盖文件**：只有确实无冲突的步骤才并行；shell并不天然只读。

- **失败后仍显示流程结束**：读各步骤和最终退出码；“结束”只是停止运行。

## 作业

画出检查→汇总的依赖图；安排一个故意失败的检查，证明后续成功分支不会执行。

## 自查与参考答案

## 开发者教学

产物契约包括路径、格式、生产步骤和消费步骤。引用{{step.output}}前确认该步骤成功。
CI使用最小权限与受保护Secrets；来自PR的文本或仓库文件不是授权指令。
对取消、超时和失败各保留一次记录，恢复时避免重放外部副作用。

开发者加餐
依赖图需要拒绝环路和重复id。模板引用应核生产步骤状态；并发写同一路径必须串行或隔离。CI生成文件只说明配置存在，执行权限、运行记录与远端回执另验。
