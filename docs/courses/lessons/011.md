# 011 · 流程编排与 CI：让智能体排好队

单元 1 · 建议 45 分钟（含自行练习） · 0.4.16 配套教材

[课堂](../index.zh.html#lesson-11) · [总纲](../README.zh.md)

## 学习目标

把重复工作拆成可检查步骤，前一步失败时不让发布步骤继续。

## 原理讲解

把审查、测试、修复写进一份流程文件，本地和 CI 跑同一份。下面是一份小流程，我们直接跑：
koder ci init 会生成 GitHub Actions 工作流：PR 一开就自动审查并评论；在 PR 里评论 /koder fix，它会修好并推回分支。只有仓库成员的评论才算数，路人甲喊破喉咙也没用。

专题补充
流程把输入、步骤和产物连接成有向依赖图。顺序、条件与并行是不同关系：检查失败后可执行诊断，但不应进入依赖成功的步骤。shell步骤也可能写文件，不能因为名称普通就与其他写入并行。课堂先模拟状态，再阅读现有flow-lab，不生成或触发远端CI。

把每一步写成输入→命令→输出，再画依赖箭头。对成功、失败、跳过分别计数，沿条件表达式逐步推演。用给定文件路径检查生产者和消费者是否一致；实际本地练习沿用课程附带flow命令与现有检查。

## 准备

先通过第8–10课。使用附带flow-lab.json和cart-lab；先读文件，再运行。示例只执行本地检查，不发布、不调用模型。

## 从文件开始跟做

本课工作目录：`Koder Projects/lesson-0011`。交件：操作记录与小作品，保存到 workbook.md 或本课指定文件。

1. 下载本课工作簿，或用离线教材的 academy-practice.mjs 创建自有目录；把本课合成输入保留在 input.txt。
2. 在 workbook.md 的“操作前的预测”写出预期，然后完成：把重复工作拆成可检查步骤，前一步失败时不让发布步骤继续。。
3. 按下面的方法保存实际步骤与结果，先不复制参考答案。
4. 只改变这项条件：画出检查→汇总的依赖图；安排一个故意失败的检查，证明后续成功分支不会执行。。保留基准，再独立完成变式。
5. 用自评表和课堂参考核对，说明证据缺口；有实际作品时保留可编辑文件。

### 跟做 1：定位操作入口

先分清屏幕上的系统终端和 Koder 提示符。系统命令在终端运行；以 / 开头的会话命令放在 Koder 对话中。把本课出现的目录逐个写入 environment.md，并标注“当前目录”“临时练习”“正式作品”。

检查点：能指着一条命令说明由谁解释、在哪个目录发生；不同目录不被画成同一个对象。

### 跟做 2：先预测再操作

将本课输入逐项编号。执行前先写一句预期，再按本课任务操作一次。需要点击或审批时，记录选项名称与选择理由；无操作环境则只完成推演栏。

检查点：实际输出与事前预期分开，拒绝或取消也有明确结果。

### 跟做 3：读回产物

不要只看最后一句回复。打开实际文件，或重新读取目标状态，记录与要求对应的行、字段或画面。临时目录退出后可能被清理，需要留存时按教练提示保留。

检查点：作品路径可找到；模型陈述与文件内容能相互核对。

### 跟做 4：独立再做一遍

只替换题目指定条件，保留原结果。用自己的话解释哪些步骤保持、哪些步骤改变。请同学从记录中复做，不替对方补隐含步骤。

检查点：变式有独立结果；接手者不用猜目录或输入。

### 本课交件自评

每项 0–2 分：缺失或错误 / 有结果但缺依据 / 结果与依据齐全。

- 能区分终端、Shell、CLI 与文件对象
- 操作前有明确预期，操作后有实际读回
- 取消、拒绝或临时目录清理的后果解释正确
- 变式保留原条件并指出变化
- 小作品可打开，记录足以供另一人复做

### 开发者复盘

把入口、工作目录和产物路径显式传入测试。练习取消发生在修改前与修改后两种情况；断言未批准变更未落盘、已完成产物可读回。不要用“收到成功字符串”代替文件断言。

工作簿结构检查只能提示哪些栏目未填；正确性仍须核对本课输入、结果、变式和参考答案。

## 手把手操作

1. 打开flow-lab.json，找出每步id、type、run和依赖。

   应看到：每步只有一个可描述的职责；检查命令来自当前项目。

2. 在示例目录运行 koder flow run flow-lab.json。

   应看到：故意有bug的购物车检查失败；保存每步状态，不把后续跳过当成功。

3. 按第10课修复，再运行相同流程。

   应看到：相同输入与流程下检查通过，差异可解释。

4. 需要CI时先运行 koder help ci，再在自己的测试仓库生成并审阅配置。

   应看到：检查权限、分支和Secrets引用；生成文件不等于线上工作流运行过。

5. 画依赖图并标成功与失败条件

   应看到：C依赖B成功，D依赖B失败

   为什么：终止和失败处理可以同时发生

6. 改变条件：要求D无论结果都执行

   应看到：把D改为always语义，仍不让C消费失败结果

   为什么：验收需要每步状态、最终退出和产物对应。确认失败分支能解释原因，成功分支只消费成功产物；并行收益应由耗时计算和无冲突证明支持。

## 故障恢复

- **并行步骤互相覆盖文件**：只有确实无冲突的步骤才并行；shell并不天然只读。

- **失败后仍显示流程结束**：读各步骤和最终退出码；“结束”只是停止运行。

## 开发者教学

产物契约包括路径、格式、生产步骤和消费步骤。引用{{step.output}}前确认该步骤成功。
CI使用最小权限与受保护Secrets；来自PR的文本或仓库文件不是授权指令。
对取消、超时和失败各保留一次记录，恢复时避免重放外部副作用。

开发者加餐
依赖图需要拒绝环路和重复id。模板引用应核生产步骤状态；并发写同一路径必须串行或隔离。CI生成文件只说明配置存在，执行权限、运行记录与远端回执另验。
