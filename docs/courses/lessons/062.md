## 学习目标

完成「先复现再修：给bug一个最小用例」的操作练习，能够解释结果、诊断常见问题并提交可核对的作业。

## 原理讲解

修复前必须证明当前实现会在一个具体输入上失败。最小复现避免环境噪声，能说明修复针对什么。若测试一直通过，可能未触发问题或断言太弱；此时应改进复现，不该为了“红灯”随意破坏代码。原错误和失败输出要保存。

专题补充
购物车缺陷报告写着“有时少算钱”。调查者需要把大订单和界面行为缩减为一个确定输入。复现的目标是让另一个人运行一次就看到同一条错误，而不是保存一大段无法归因的日志。 故障必须包含触发输入、独立预期、实际结果以及失败位置；缩减条件时保留真正导致偏差的因素，不能顺手修改业务答案。

沿输入、执行路径、输出、断言四层缩减。差值可以帮助识别遗漏因素，但根因仍要由代码路径支持。负例应在旧实现失败，在修复实现通过；环境启动失败不能充当这个负例。

## 示例与解读

```text
import assert from "node:assert/strict";
assert.equal(total([{price:200,qty:3}]),600);

补充案例：把整张订单缩到一行
合成 Node 程序：
(async()=>{const broken=xs=>xs.reduce((s,x)=>s+x.price,0);const input=[{price:200,qty:3}];return {actual:broken(input),expected:600,delta:broken(input)-600};})().then(value=>console.log(JSON.stringify(value)));
```

错误实现返回200，断言失败；正确预期由数量规则独立计算。

### 跟做 2：定位最小改动

根据第一次不一致定位函数或分支。修复先写失败用例；重构固定行为；优化固定正确结果并记录数据规模。

检查点：改动目标明确，不以全仓格式化或新增无关依赖代替修复。

7. 先按数据逐项推演“把整张订单缩到一行”，再将完整程序保存为自有练习目录的 case.mjs，运行 node case.mjs；对照返回值、类型与输入是否变化。

   应看到：{"actual":200,"expected":600,"delta":-400}

   为什么：唯一一行已经复现，排除了多商品排序和折扣；少400恰好是缺少两件的价格，但这还需要读取乘法是否缺失。 排错时分别排除两种误读：“qty=1通过即可否定缺陷”；“差400就能断言数据库丢了两行”。

8. 改变条件：改成qty=1会怎样，能否用它取代复现？

   应看到：实际和预期都是200，缺陷被隐藏；保留qty=3才有区分力。

   为什么：没有失败时先核查用例是否调用目标实现、是否有断言、是否读取旧缓存；有失败时看第一条异常，不把依赖缺失解释为业务复现。

## 故障恢复

- **结果与示例不一致**：测试未导入目标函数或没有断言，也可能退出0；先确认实际执行路径。 先保存原始错误，再从第一次偏离预期的步骤定位。

- **当前环境不能完成真实操作**：完成资料阅读、合成演练和验收计划，标明缺少的账号、运行时或设备。不要伪造回执，也不要为了过课扩大授权。
