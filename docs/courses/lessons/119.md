## 学习目标

完成「验收报告：让PASS有可追溯依据」的操作练习，能够解释结果、诊断常见问题并提交可核对的作业。

## 原理讲解

报告应把源代码审查、本地测试、真实模型、真实账号、真实设备和生产发布分层。每条PASS绑定命令、版本与产物，FAIL保留原始输出，NOT_RUN说明缺什么条件。UNKNOWN表示操作结果无法确认，不应塞进未运行或失败。

专题补充
验收报告让他人知道测了什么、在哪测、结果是什么以及证据在哪里。源审、本地夹具、真实模型、真实账号、目标设备与生产各回答不同问题。PASS必须绑定具体检查；UNKNOWN不能塞进失败或未运行来简化表格。

先按目标拆验收项，再给每项记录前置、版本、命令或动作、结果与原始证据。汇总时只提升已有证据支持的结论，保留旧失败和后续修复时间线。

## 准备

先完成第118课。使用自有Koder Projects练习目录和合成数据；阅读示例不会执行命令。需要运行脚本时先核对本机运行时；不为阅读课程自动安装任何软件。

### 跟做 1：从风险写预期

先列本课要防止的错误，再写应通过和应失败各一个输入。预期由业务规则推导，不能复制待测函数输出当答案。

检查点：每条检查都有失败含义，空结果不会自动算通过。

### 跟做 2：证明检查能失败

在自有副本中故意破坏一处相关输入或实现，运行同一检查，保存失败输出后恢复。不要删断言来让基线变绿。

检查点：能看到对应断言失败或非零退出，证明入口确实被调用。

### 跟做 3：固定条件再复测

保留版本、命令、cwd、数据和退出码。不同平台或账号层独立记录；复测仍使用原断言与合理时限。

检查点：通过结果对应当前文件；历史失败也保留。

### 跟做 4：做接手者复现

复制验收包到新目录，只按 README 操作，补全隐含前提。变式后说明哪些检查失效、哪些需要新增。

检查点：另一人能从说明找到输入、命令、预期和实际结果。

   应看到：记录与「状态含义一致，摘要能跳到原始证据。」逐项对照，不把未执行项填成通过。

7. 分别标PASS、FAIL、NOT_RUN、UNKNOWN 将上述完整程序保存为自有目录的 case.mjs，运行 node case.mjs；先独立预测输出，再与固定输出对照。

   应看到：四项语义不混用
   Node 固定输出：&#91;{"id":"A","status":"PASS"},{"id":"B","status":"FAIL"},{"id":"C","status":"NOT_RUN"},{"id":"D","status":"UNKNOWN"}&#93;

   为什么：未知效果已尝试，不能叫未运行

8. 改变条件：D后来查到匹配回执

   应看到：追加确认结论，保留原先未知事件

   为什么：检查版本对应、证据路径可读、实际运行与计划分开。没有数据不能写0失败；报告引用的截图或日志必须对应本次目标，不能挪用邻近任务。

## 故障恢复

- **结果与示例不一致**：计划、工具声明和自评都不能替代实际结果。 先保存原始错误，再从第一次偏离预期的步骤定位。

- **当前环境不能完成真实操作**：完成资料阅读、合成演练和验收计划，标明缺少的账号、运行时或设备。不要伪造回执，也不要为了过课扩大授权。

至少提交明确产物、关键步骤记录和一项失败或边界检查。结合本课判断题核对：应写NOT_RUN并说明条件。 对真实设备或外部服务没有执行的部分写NOT_RUN。

## 开发者教学

报告生成可自动汇总，但不得自动将缺失字段转PASS。
实现前固定输入、输出、错误与权限契约。为本课关键边界设计一个应通过与一个应拒绝的用例。
交付时记录源码/配置版本、实际命令、退出码、产物及回退方式；静态检查不替代真实账号或设备验收。

开发者加餐
证据存储与状态投影分开，状态更新不能先于可靠回执。摘要可裁剪，原始记录需可追踪；敏感材料应脱敏并说明变换，不创造不存在的原件。
