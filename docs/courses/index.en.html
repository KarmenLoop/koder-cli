LESSON 01 / 30 · 25 MIN

Welcome to Koder boot camp

Distinguish the system shell, Koder chat and the practice project; finish an offline exercise and locate its files.

Before you start

Use a terminal with copy and paste. Read the installation guide if needed; do not reinstall a working copy. The coach uses a temporary directory, retained only if you choose to keep it. Use a separate folder for extended exercises.

Step by step

  1. Run koder --version in the system shell, note the version, then run koder help.

    Check · Both commands return readable output. If the executable is missing, use lesson 16 before continuing.

  2. Run koder learn and select your actual shell in lesson 1.

    Check · A practice path appears. The scripted coach makes no paid model calls, but its file edits and tests are real.

  3. Press Enter to continue, jump to lesson 4 with 4, reject one edit and accept another. Quit with q, then reopen koder learn.

    Check · Progress can resume. Quitting normally removes the practice files; saved progress does not mean saved project files.

  4. For your own work, leave the lesson and run koder project create "Learning Site" --kind website, then koder project list --json.

    Check · The project has its own directory. Use the returned path instead of guessing or reusing a temporary practice path.

If something fails

The cart disappears after q

This is practice cleanup. Choose to keep it in the graduation lesson if you need the files.

The shell does not recognize /setup

Enter koder chat first, or use koder setup in the shell.

Assignment

Write a learning record with version, shell, project path and temporary practice path. Identify which steps are offline and which need your model.

Show acceptance criteria

All four values must come from actual output. The learn coach is offline; ordinary ask/run uses the configured model. Temporary exercises are not durable deliverables.

Developer: design and validation

  1. Record the command, version, working directory, exit code and artifact path.
  2. Run node --test in the bundled cart-lab first and observe the planted failure; then ask Koder to fix it and inspect the diff.
  3. Require a failing baseline, passing checks and the resulting files. A model completion message is not evidence.
  4. Keep teaching examples separate from live-account acceptance.

LESSON 02 / 30 · 20 MIN

The banner and the prompt

Read the active directory, model and mode, and find help without mistaking the prompt for a completed task.

Before you start

Complete lesson 1, widen the terminal to at least 80 columns and prepare a harmless task.

Step by step

  1. Run koder and read the version, model and directory before entering a task.

    Check · The directory must match your project. A displayed model name is configuration, not a connectivity test.

  2. Enter /help, then /setup; exit Setup back to the conversation.

    Check · Help and Setup open in the current CLI session.

  3. Press / on an empty line, select with arrows and fill with Tab. Edit before submitting.

    Check · Selection fills a draft. Esc closes the menu; use /help or completion if the terminal cannot render it.

  4. Open Koder in a different project in a second window and inspect both directories.

    Check · Each window should work independently. Preserve the full occupancy message if you intentionally share a session.

If something fails

Broken borders or wrapped menu

Widen the window or choose a plain banner in Setup; retain model settings.

A session appears occupied with one window visible

Record version and session name; inspect other terminals or residency before deleting anything.

Assignment

Annotate a redacted banner with version, directory, model and mode. Fill a menu draft, then cancel it without sending.

Show acceptance criteria

Explain the difference between configuration and execution. Canceling the draft must create no model task or file edit.

Developer: design and validation

  1. Treat selection, draft insertion, submission and cancellation as separate events.
  2. Check the menu at 80×24 and in a narrow terminal; fallback must remain readable.
  3. For non-TTY/JSON calls, verify that animation and menus do not pollute output. Check session boundaries with two separate projects.

LESSON 03 / 30 · 35 MIN

Configure a model: give Koder a brain

Configure the service, protocol and model your account actually supports, then test text and tool round trips separately.

Before you start

Have your product type, model ID and official base URL ready. Supply the key only through the dedicated input or a secret manager. Live diagnostics may incur charges.

Step by step

  1. Open model settings in koder setup. Choose region and metered API or plan before the model.

    Check · The route matches the key. Disabled entries remain unavailable; a web subscription is not API credit.

  2. Save the key, then run koder model show to inspect the model, protocol and address.

    Check · Settings match your console. Review and redact output before sharing it.

  3. Run koder model test, followed by koder model test --tools after success.

    Check · Keep both results. Text success with tool failure is not a working agent integration.

  4. Use koder model presets and koder model models <preset-id> where supported; compare with help and your console.

    Check · Discovery and account access are different. Refreshed model metadata does not grant quota.

If something fails

HTTP 401/403

Check region, product, permissions and key validity instead of repeatedly retrying.

422 with 1026/1027

Treat it as MiniMax content filtering; use lesson 22 to isolate input, not as a connectivity outage.

Assignment

Create a key-free connection card: preset, model, protocol, base URL, text result, tool result and billing source.

Show acceptance criteria

Support each field with configuration or output. Mark unrun checks NOT_RUN rather than assuming success.

Developer: design and validation

  1. Use --key-env VARIABLE_NAME for a secret variable in CI, never the key value in arguments.
  2. Use local fixtures for success, 401, 429, 5xx, content filtering and tool-protocol errors; check classification and redaction.
  3. Keep diagnostic deadlines separate from long-task retry budgets, and distinguish fixture results from paid calls.

LESSON 04 / 30 · 30 MIN

First task: read the diff, decide

Turn a vague request into a verifiable deliverable; inspect the diff and check the disk after rejecting or approving it.

Before you start

Use the coach cart or bundled cart-lab, not a critical project. Record existing changes before working in your own repository.

Step by step

  1. Ask: “Fix cart totals so quantity is counted; preserve other behavior, test an empty cart and run node --test.”

    Check · The request specifies scope, constraints and a check, rather than only “improve it”.

  2. Inspect the proposed files and diff; reject the first edit.

    Check · The file remains unchanged. Verify it rather than relying only on the reply.

  3. Retry and approve only the target function and relevant tests.

    Check · Changes stay in the project and do not add unrelated formatting or dependencies.

  4. Open the files, run the check and request a list of changes, validation and remaining work.

    Check · Files, test output and the report agree. Preserve output if the check fails.

If something fails

Only advice, no files

Use an execution task with file targets and checks; confirm you are not in ask or plan mode.

Execution result is unknown

Inspect files and receipts before asking for a full replay.

Assignment

Add a zero-quantity case to cart-lab, fix the implementation and retain before/after test results and the diff.

Show acceptance criteria

An empty cart is 0; 200 cents ×3 plus 150 cents ×1 is 750; zero quantity contributes 0. Keep existing tests.

Developer: design and validation

  1. Translate the requirement into inputs, outputs, edge cases and invariants. Write tests that catch the actual bug.
  2. Use git diff --check and inspect the diff; passing tests do not justify deleted assertions.
  3. Record workspace, files, checks and exit codes. A final reply is not a file deliverable.

Assuming accept grants everything

Inspect feature states; license acceptance has no such meaning.

List the separate decisions for license acceptance, model access to mail and automatic replies.

Show acceptance criteria

None substitutes for another; sending must follow final confirmation or an explicitly authorized rule.

Developer: design and validation

  1. Model consent separately from availability; test defaults, migration and revocation.
  2. Retain prior settings and never enable sensitive sources through an upgrade.
  3. Name the missing layer in diagnostics rather than suggesting disabling protection.
