# Website delivery

Website creation and substantial redesign use the bundled Fullstack Web Delivery Skill. The original Skill and its 29 resources remain unchanged at v0.9.1, commit `72e05993c485210e255c1e950f424a53fb05be49`. Its KarmenLoop source-available license permits exact redistribution with notices; it is not an open-source license. Koder's integration is separate host code.

The model receives the actual Skill text and relevant reference material within its context budget. The packet identifies partial resources and the next offset for `skill_read`. Reading the packet does not execute its scripts, establish acceptance, or grant tool permissions. Setup can disable this workflow without disabling the ordinary implementation checks.

A new site follows the relevant stages: establish scope, reuse or discover requirements, deliver the complete plan and specifications, compare layouts, select a direction, implement working pages and applicable business flows, verify, and hand over. Static sites do not require accounts, a database or an admin interface. Existing-site repairs retain their project anchor and scope.

For a new site, save the plan in `PLAN.md` or the existing `docs/web-delivery` plan. Use `project_visuals review` for three layouts. After the review, a terminal `ask_user` can offer all three complete layout names. `project_visuals select` verifies its actual answer in the current task and records `terminal-choice`; model-authored claims, old answers, conflicting choices and negative/combined options do not count. Alternatively, it records a reasoned, reversible agent choice when the user delegated selection or the host is noninteractive. An explicit request to wait for the user's choice takes precedence. Agent selections are recorded as `agent-assumption`; browser feedback is recorded separately. Keeping a selected layout or explicitly skipping the comparison avoids repeating that stage.

Use the existing file and shell tools to implement the site. `workspace_preview discover` checks for an existing development script or a conventional Node HTTP entrypoint before falling back to static HTML. `workspace_preview start` requests the normal command approval for that entrypoint, starts an owned process, and waits up to two minutes for a successful loopback response. It does not install dependencies. Vite and Next.js receive explicit local host and port arguments; other scripts must honor `HOST` and `PORT`. A pre-existing server can still be attached with `start url`. Include the actual preview address and startup instructions in the handoff.

The approved startup file is hashed and checked again before execution. Rejecting approval starts nothing. Startup cancellation, timeout and process exit return explicit failure codes; a static HTML fallback cannot satisfy the backend delivery check. A successful preview retains its supervised process until `/preview stop` or CLI exit, rather than applying the ordinary foreground shell deadline to a development server. The supervisor uses the existing command-tree cleanup implementation and stops when its IPC owner disappears. External servers are never adopted for termination. A repeated start reuses the owned backend. Changing a static preview to a backend updates the same preview panel and refresh target.

The local process, HTTP API and cleanup checks have run on macOS. Windows and Linux code paths use the same owner protocol and existing platform process cleanup, but this revision's native desktop and process-tree checks remain `NOT_RUN` on those systems. HTTP readiness is not browser or application acceptance.

Pending automatic preview work settles before the next model request and completion review. The model receives the owned preview's actual address as host status, which does not count as a tool receipt or browser acceptance. `workspace_preview start` accepts `open:false` for HTTP preview without launching a browser; a task that explicitly excludes opening the browser keeps that constraint even when the option is omitted. Turning automatic preview off does not by itself satisfy the preview check. Explicitly excluding preview narrows the delivery scope and suppresses the automatic project-map preview.

For new sites and substantial redesigns, completion checks require current source, an applicable plan and layout evidence, and a live response from Koder's owned local preview. They reject nonexistent or empty source, invented preview addresses, stopped previews, and a review or file-index page presented as the website. Framework component source with an existing startup script is supported; generated HTML is not required for the file-structure check. A user who explicitly excludes preview keeps that narrower scope. Existing-site repairs check the affected source without requiring a new whole-site plan, layout comparison or preview.

A bare “continue” can resume the nearest unfinished website request when a saved host record establishes that it is incomplete or interrupted. It does not revive an older site across an unrelated request or trust an assistant's claim that work remains. Saved verified writes are checked against the current file hashes before they count toward the resumed task. The remaining preview can then be completed without rewriting valid source. Disabling the fullstack workflow removes its plan and layout gates while retaining source and preview checks and any other enabled skills' own policies.

The checks report their limits. A local HTML response establishes HTTP availability, not rendered layout, working controls, mobile usability, accessibility or complete business acceptance. Report browser checks as `NOT_RUN` until operated. Production deployment, external integrations, account access and publishing retain their original authorization requirements.

Preview ownership is process-local. If `status`, `open` or `stop` returns `not-owned`, the previous preview may still be running elsewhere. Read-only verification of its saved URL can establish availability; do not claim it stopped or start a duplicate merely because the current process has no owner. A new preview still follows the original task authorization.

Explicit instructions to continue the current website retain the nearest unfinished task and revalidate prior write hashes against current files. Root-bound completion state persists across memory restoration. This does not reauthorize old actions or replay unknown effects. Negative wording such as “do not redo completed work” does not request a redesign.
