# 上下文窗口与自动压缩

适用于 Koder CLI 0.5.1。

在聊天中输入 `/context`，或在终端运行 `koder context status`，可以查看当前模型的窗口、输出上限和自动压缩设置。尚未配置模型时，也可以调整压缩偏好。

这里有三项独立设置：

| 设置 | 决定什么 | 设置入口 |
| --- | --- | --- |
| 模型窗口与输出上限 | 当前型号、接口和账号实际可用的容量，以及每次回答的输出上限 | `context set --context-window … --max-output …` |
| 自动压缩 | 何时为模型请求节选较早历史，以及优先保留多少近期轮次 | `context on/off`、阈值与轮次设置 |
| Headroom | 将适合的工具结果改成可还原的紧凑表示 | Setup → 技能 → Headroom 上下文优化 |

自动压缩不会扩大模型窗口。Headroom 的设置和详细行为见 [Headroom 上下文优化](HEADROOM.zh.md)。

## 第一次设置：使用菜单

1. 在终端输入 `koder setup`。已经在聊天中时，输入 `/setup`。
2. 选择“上下文与输出”。
3. 选择“模型窗口与输出上限”，先填写 `contextWindow (tokens)`，再填写 `maxOutput (tokens)`。请按服务商对当前型号、所用接口和账号的实际限制填写。第二项保存后会显示“上下文配置已保存”。现有模型名称、接口地址和密钥会保留。
4. 回到上下文子菜单，选择“自动压缩”即可在开、关之间切换。
5. 选择“压缩触发与目标占比”，先填写触发占比，再填写更小的目标占比。两个数值都提交后才保存；中途按 Esc 会取消这次阈值修改。
6. 选择“优先保留近期轮次”，输入 0 至 100 的整数。
7. 需要恢复初始偏好时，选择“恢复默认压缩设置”。它恢复开启、80% 触发、60% 目标和最近 4 轮；模型窗口、输出上限、密钥和 Headroom 设置保持原值。
8. 按 Esc 返回主设置菜单，再按 Esc 返回聊天或终端。

尚未配置模型时，第 3 步需要先配置模型，其余压缩选项仍可使用。菜单显示项目所选模型时，窗口修改也作用于该模型。

## 默认值和有效范围

| 设置 | 默认值 | 有效范围 |
| --- | --- | --- |
| 自动压缩 | 开启 | `on` 或 `off` |
| 触发占比 | 80% | 整数，必须大于目标占比且不超过 99% |
| 目标占比 | 60% | 整数，至少 1%，必须小于触发占比 |
| 优先保留近期轮次 | 4 | 0 至 100 的整数 |
| 模型窗口 | 取当前模型配置 | 2,048 至 16,777,216 的整数 |
| 输出上限 | 取当前模型配置 | 至少 256 的整数，严格小于模型窗口 |

一个轮次通常包括一条用户请求，以及随后关联的助手回答和工具调用。近期轮次是优先保留的偏好：大段内容仍可能被节选，必要时也可能让出空间。设置为 0 不会允许删除当前请求；设置为 100 也不会让请求越过模型窗口。

模型窗口没有适用于所有型号的统一默认值。配置值可来自型号默认、预设或已有模型记录；服务商公布的最大窗口，也可能高于某个代理接口或账号实际支持的额度。填写更大的数字只会改变本地预算判断，不会为服务商开通更大窗口。

## 用命令修改

查看设置：

```sh
koder context status
koder context status --json
```

调整压缩偏好：

```sh
koder context set --trigger-percent 85 --target-percent 60 --keep-turns 6
koder context off
koder context on
koder context reset
```

`on` 和 `off` 只改开关，保留阈值与轮次。`reset` 只恢复压缩默认值，也可以用于修复手工编辑造成的无效压缩设置。改变数值时使用 `set`；不要将数值参数附在 `status`、`on`、`off` 或 `reset` 后。

调整当前模型的窗口和输出。以下数值仅为命令示例，使用前应核对接口限制：

```sh
koder context set --context-window 128000 --max-output 8192
```

窗口和输出写回原模型记录，现有凭据与接口地址保留。只传 `--context-window` 时，输出上限按原有规则取“旧输出上限”和“新窗口的四分之一”中的较小值；希望明确控制两项时，请同时传入。

选择已保存的命名模型，使用的是配置名称，而非服务商的型号 ID：

```sh
koder model list
koder context status work
koder context set work --context-window 128000 --max-output 8192
koder context set --model work --context-window 128000 --max-output 8192
```

不指定名称时，命令遵循当前项目和模型选择。可以用 `-w` 指定项目：

```sh
koder context status -w ./my-project
koder context set -w ./my-project --context-window 128000 --max-output 8192
```

压缩偏好保存在当前 CLI 用户配置中，供该配置下的会话共用；附带模型名称不会创建一份该模型专属的压缩策略。

### 环境变量模型与外部配置文件

只通过 `KODER_MODEL`、`KODER_BASE_URL` 等环境变量配置的模型，可查看窗口，也可修改压缩偏好。它的窗口由 `KODER_CONTEXT_WINDOW` 和 `KODER_MAX_OUTPUT` 控制，`context set` 不会把它覆盖成磁盘模型。

例如，在 macOS、Linux 或其他支持 `export` 的 shell 中设置当前终端：

```sh
export KODER_CONTEXT_WINDOW=128000
export KODER_MAX_OUTPUT=8192
koder context status
```

在 PowerShell 中：

```powershell
$env:KODER_CONTEXT_WINDOW = "128000"
$env:KODER_MAX_OUTPUT = "8192"
koder context status
```

这些示例仍需配合已有的模型与接口配置。若项目选择了已保存模型，该项目选择继续生效。

使用 `--provider path/to/provider.json` 时，可以查看实际配置文件的窗口。外部文件在这个设置入口中只读；修改窗口前请选择已保存模型的名称。命令不会悄悄改写全局默认模型。

## 在当前聊天里调整和查看

聊天命令与终端命令对应：

```text
/context
/context set --trigger-percent 85 --target-percent 60 --keep-turns 6
/context off
/context on
/context reset
/context status --json
```

设置命令本身不发起模型请求。内置 Koder 引擎在后续请求中使用保存的压缩策略；其他终端修改同一用户配置后，后续请求也会读取新策略。窗口修改仍按当前模型选择生效。

`/context` 可显示本会话上次请求的占用估算。刚打开会话、尚无可用记录时，JSON 中的 `lastRequest` 为 `null`。单独启动的 `koder context status` 主要用于查看配置，不会连接另一个正在运行的聊天获取实时用量。

JSON 的 `contextCompaction` 是当前设置，`model` 是当前选中的模型。`lastRequest` 是上次记录的请求数据；修改设置后，它不会自动变成新设置下的试算结果。

| `lastRequest` 字段 | 含义 |
| --- | --- |
| `estimated` | 请求消息的 token 数估算 |
| `toolTokens` | 工具定义的 token 数估算 |
| `output` | 本次请求的输出预留 |
| `window` | 该请求采用的模型窗口 |
| `compaction.triggered` | 是否达到自动压缩触发条件 |
| `compaction.applied` | 是否实际改变了发送给模型的上下文 |
| `compaction.beforeTokens` / `afterTokens` | 压缩前后的预算估算 |
| `compaction.removedMessages` / `compactedMessages` | 请求中移除或改成节选表示的消息计数 |
| `compaction.reason` | 未触发、已达目标或受保护内容等原因 |

压缩前后总量包含配置的输出预留；`output` 是适配窗口后本次请求实际预留。因此总量可能仍高于软目标，而实际请求使用较小的输出预留。

这些数字属于本地估算，不是服务商账单 token、缓存命中或费用节省凭证。实际上采用历史压缩时，聊天会给出简短提示；没有变化时不会反复提示。

## 触发、目标和超窗错误

触发判断使用“完整输入估算 + 工具定义估算 + 输出预留”，再与模型窗口比较。默认达到 80% 时尝试压缩，目标为约 60%。输出预留也占用窗口，并非输入以外的额外容量。

目标占比是尽力达到的值。当前请求、系统内容、近期轮次和受保护记录可能使请求仍高于目标；达到触发阈值也不代表一定能减少内容。输出上限是上限，实际请求预留还会受剩余空间约束。

关闭自动压缩后，Koder 保留完整历史用于请求，仍遵循必要的协议恢复处理。某些服务商需要未保存在磁盘的私有推理状态，恢复会话时不能编造这些状态或原样重放缺少状态的旧协议调用；可见历史可能以引用资料的形式恢复。Headroom 若仍开启，也会继续对符合条件的工具结果使用可还原表示。

输入和工具定义无法容纳在硬窗口内时，命令报告 `CONTEXT_BUDGET_EXCEEDED`，保存的历史和原始工具回执保留。可以按情况处理：

1. 核对实际模型与接口额度，纠正填写过小的窗口。
2. 根据所需回答长度减少输出上限，留出更多输入空间。
3. 需要节选历史时开启自动压缩，并调整阈值或近期轮次。
4. 减少当前请求中不必要的大段材料，或改用实际支持更大窗口的模型。

单纯提高本地数字不能修复服务商的真实限制。失败也不表示之前的工具操作已经撤销；继续前仍须核对已有回执。

## 历史、执行状态与适用范围

自动压缩只改变发送给模型的内容，不替换磁盘中的完整会话历史，也不建立第二套记忆存储。节选不是新指令、批准或执行成功的证据。

未完成、`pending`、`UNKNOWN` 和未确认的工具记录受到保护。签名协议组在硬窗口以内原样保留。开启压缩后，如果完整且已返回的签名调用组仍超出硬窗口，可将整组转换为可见回执引用：保留调用身份、参数和工具结果，助手可见文本可以节选，私有块与签名一并移除。不会把修改后的文本与旧签名混用；未完成或结果未知的调用组、关闭压缩时均不走此转换。工具调用和对应结果按组处理，不能凭一段摘要把未知结果当成成功，也不能因此重放操作。原有权限、费用预算、费用预留和取消流程继续生效。

内置 Koder 引擎的主聊天、`ask`/`run`、子 Agent 和 MoA 模型请求使用同一用户压缩策略；各请求仍受各自模型窗口与输出上限约束。恢复的会话保留其原始历史。Hermes/ACP 等外部引擎有自己的上下文处理，本指南不保证这些设置能控制其内部请求。

### 保存失败时

混合修改模型窗口与压缩偏好时，会先验证全部参数。参数无效时不会先保存其中一部分。两份配置文件仍按顺序写入；若第二步或文件后续操作失败，可能出现 `CONTEXT_SAVE_PARTIAL`。请按提示查看哪些内容已保存，再运行 `koder context status` 核对并重试未保存项。

本指南说明设置与行为，不是付费模型质量、费用、设备兼容或发布验收报告。

是否写入磁盘仍遵循原有记忆设置。`--no-memory` 的当前会话记录只留在内存中；上下文压缩不会静默开启磁盘记忆。
